# 認証とアカウント

ログインの方式、外部のアカウントとの結び付け方、セッションと CSRF、アカウントの削除について、コードを読む前に知っておくと迷わないことをまとめる。
モジュールの全体の配置は docs/architecture.md、テーブルと列は docs/data-model.md を見る。

## 前提: ユーザーID はメールアドレス

- `users.username` がユーザーID で、利用者のアカウントではメールアドレスを兼ねる。保存と照合は `auth::normalize_username` で正規化した値で行う。
- 外部のアカウント (Google・LINE・Apple) とメールでのアカウントは、このメールアドレスで1つのアカウントにまとまる。
- メールアドレスでないユーザーID (CLI や管理画面で作ったもの) もそのまま使える。メールを送る処理は、宛先がメールアドレスでないアカウントには送らない (`Mailer::can_send_to`)。
- `users.email_verified = 0` のアカウント (サインアップの確認待ち) は、ログイン・管理 API・削除予約のどれからも「存在しない」として扱う。

## ログインの方式と主なファイル

| 方式 | 有効になる条件 | 主なファイル |
| --- | --- | --- |
| ID/パスワード | 常に有効 | `src/auth.rs`・`src/api/auth.rs` |
| Google | `GOOGLE_OAUTH_CLIENT_ID`・`GOOGLE_OAUTH_CLIENT_SECRET` | `src/google_login.rs` |
| LINE | `LINE_LOGIN_CHANNEL_ID`・`LINE_LOGIN_CHANNEL_SECRET` | `src/line_login.rs` |
| Apple (ウェブ) | `APPLE_TEAM_ID`・`APPLE_KEY_ID`・`APPLE_PRIVATE_KEY`・`APPLE_SERVICE_ID` と、https の `[server] public_url`・`[session] secure_cookie = true` | `src/apple_login.rs` |

- 外部のログインに共通の部品 (`state`・`nonce`・PKCE の生成、連携の取り消し) は `src/external_login.rs`、ユーザーの特定と作成は `src/oauth_identity.rs` にある。
- 有効かどうかは `GET /api/v1/auth/providers` で画面に伝え、無効な方式のボタンは出さない。
- モバイルアプリは Cookie でなくトークン (`Authorization: Bearer`) でログインする。仕組みは docs/mobile-app.md。

## 外部のアカウントでのログイン

### 共通の流れ

1. `GET /api/v1/auth/{provider}/login` が `state` などを作り、専用の Cookie に入れて提供元の認可画面へリダイレクトする。
2. コールバックで `state` を Cookie の値と照らし合わせ、認可コードを提供元のトークンエンドポイントで引き換える。
3. `api::auth::resolve_external_login` が、凍結の判定 → ユーザーの特定か作成 → 取り消し用トークンとプロフィールの保存 → 削除予約の取り消しを行う。
4. `auth::establish_session` でセッションを作る。結果は成否に関わらず `/` か `/login?oauthError=<コード>` へのリダイレクトで返す (JSON は返さない)。

### `state`・PKCE・`nonce`

| 提供元 | `state` | PKCE (S256) | `nonce` | ID トークンの確かめ方 |
| --- | --- | --- | --- | --- |
| Google | あり | あり | なし | トークンエンドポイントの応答を使い、署名は確かめない |
| LINE | あり (英数字だけ) | あり | あり | LINE の検証エンドポイント (`/oauth2/v2.1/verify`) に `nonce` 付きで送る |
| Apple | あり | なし | あり | トークンエンドポイントの応答の `iss`・`aud`・`exp`・`iat`・`nonce` を手元で確かめ、署名は確かめない |

- 署名を確かめないのは、クライアントの秘密を付けて提供元と直接 TLS でやり取りした応答だから (OpenID Connect Core 3.1.3.7、Google の OpenID Connect の資料)。
- Apple は認可・トークンエンドポイントの文書に PKCE の項目が無いため、掛けない。引き換えの `client_secret` は Apple の秘密鍵で署名した ES256 の JWT で、呼ぶたびに有効期間5分で作る。
- `state` の Cookie (`src/oauth_cookie.rs`) は提供元ごとに名前を分け、並行して始めても上書きしない。有効期間は10分で、コールバックで成否に関わらず消す (使い捨て)。
  - Google・LINE は `SameSite=Lax`。コールバックはクロスサイトのトップレベル GET で、`SameSite=Strict` のセッション Cookie は届かないため、セッションとは別の Cookie にしている。
  - Apple の戻りは Apple のサイトからの POST (`form_post`) なので、`SameSite=None; Secure` にする。そのため Apple のウェブのログインは https と `secure_cookie` が揃う構成でだけ有効になる。
  - Apple のコールバック (`POST /api/v1/auth/apple/callback`) だけは同一オリジンの確認 (後述) から外し、`state` の照合で守る。
- OAuth のコールバックは、ID/パスワードのログインのレートリミッタに繋がない。乱打で ID/パスワードの利用者まで締め出さないため。

### どのメールなら既存のアカウントに結び付けるか

ここを緩めると、他人のメールアドレスを名乗った外部のアカウントから、そのアドレスのアカウントに入れてしまう。

- Google: `GoogleIdToken::email_is_trusted` を満たすものだけ受け付ける。`email_verified = true` で、`@gmail.com` か `hd` (Google Workspace のドメイン) があるもの。
  - それ以外は結び付けも新しいアカウントの作成もせずに断る (`google_email_untrusted`)。Gmail でも Workspace でもないメールで作った Google アカウントは、作った後でメールの持ち主が変わっても `email_verified = true` のまま残るため。
  - `hd` は ID トークンにしか載らないので、userinfo エンドポイントは使わない。
- LINE: ID トークンに `email_verified` に当たるものが無いが、LINE がメールアドレスの登録・変更のときに持ち主を確かめるので、そのまま信じる。メールアドレスの提供を断られたらログインさせない (`line_email_required`)。
- Apple: `email_verified` が true でメールアドレスがあるものだけ受け付ける。「メールを隠す」を選んだ人の転送用アドレス (`@privaterelay.appleid.com`) は既存のアカウントと一致しないので、新しいアカウントになる。

### ユーザーの特定と作成 (`oauth_identity::find_or_create_user`)

1. `oauth_identities` を `(provider, subject)` で探す。利用者は提供元の `sub` で見分ける。
2. 無ければ、同じメールアドレスの既存アカウントに結び付ける。結び付けるのは `email_verified = 1` で、まだその提供元と連携していないアカウントだけ。
   - 連携済みのアカウントに別の `sub` を足さないのは、Workspace などでは同じメールアドレスが別人の新しいアカウント (別の `sub`) に割り当て直されうるため。
   - 条件の確認と INSERT は1文で行い、別々の `sub` からの同時ログインが両方とも結び付くのを防ぐ。
   - 同じアドレスの未確認のアカウントは、先に確認済みにしてから結び付ける。未確認のアカウントはパスワードも記録も持たないので、引き継いでも誰かの持ち物を渡すことにならない。
3. それも無ければ、使えないパスワードハッシュ (`password_usable = 0`) の新しいアカウントと `oauth_identities` の行を作る。
- 凍結の判定は結び付けより前に行う。結び付けはやり直せないので、断るログインで `oauth_identities` に行を残さないため。
- プロフィール (`display_name`・`avatar_url`) は、Google・LINE ではログインのたびに上書きする。Apple は名前を最初の承認のときにしか渡さないので、渡ったときだけ名前を入れる。`avatar_url` はホストのある https の URL だけを受け付ける。

### 連携の取り消しと解除

- LINE の開発ガイドラインと App Store 審査ガイドライン 5.1.1(v) により、退会と連携の解除では提供元の側の連携も取り消す (`external_login::revoke_link`)。Google は取り消さない (トークンを持たない)。
- 取り消しに使うトークンは `oauth_identities.refresh_token`・`access_token` に、XChaCha20-Poly1305 で暗号化して保存する (`src/token_cipher.rs`)。
  - 鍵は環境変数の秘密 (LINE はチャネルシークレット、Apple は秘密鍵) から導く。DB やそのバックアップが漏れても、鍵が一緒に漏れないようにするため。
  - LINE はウェブのログインでリフレッシュトークン、アプリのログインでアクセストークンを保存し、取り消しではリフレッシュトークンを先に試す。ログインで受け取らなかった方は前の値を残す。
  - Apple はリフレッシュトークンを、発行した側 (ウェブのサービス ID かアプリの Bundle ID) と一緒に暗号化する。取り消しにはその `client_id` が要るため。
- 取り消せなくても (トークンの期限切れ・秘密の変更など) 退会と解除は続け、ログに残す。
- 本人は `DELETE /api/v1/account/identities/{provider}` で連携を解除できる。解除した後にログインできる方法 (`users.password_usable = 1` か別の連携) が残るときだけで、残らなければ 409。
  - 判定と削除は1文の DELETE で行う。別々のリクエストで2つの連携を同時に外し、ログイン方法が無くなるのを防ぐため。
  - 解除しても、同じ提供元で同じメールアドレスのログインをすれば、上の規則でまた結び付く。

## ID/パスワードとメール

- パスワードは Argon2id でハッシュにする。最小の強度は `[password]` の設定で、`GET /api/v1/auth/password-policy` で画面に伝える。
- 存在しないユーザーでもダミーハッシュ (`DUMMY_HASH`、実ハッシュと同じパラメータ) と照合し、応答時間からユーザーの有無が分からないようにする。
- 凍結の判定はパスワードの照合の後に置く。先に見ると、凍結中かどうかがユーザー名だけで分かってしまう。

### レートリミット

- `auth::AttemptRateLimiter` はプロセス内のメモリで数える簡易なもので、再起動やインスタンスをまたいでは数えない。キーの数にも上限がある。
- ログインは「接続元 + ユーザー名」ごとに1分5回、接続元ごとに1分30回、全体で1分300回。
  - ユーザー名だけで数えると、第三者が本人の名前で試し続けるだけで本人を締め出せるため、攻撃者と同じ接続元だけが止まる形にしている。全体の上限は Argon2 の CPU を使い切らせる DoS への歯止め。
  - 接続元は IPv4 はアドレスごと、IPv6 は先頭 /64 ごと (`forwarded::rate_limit_key`)。接続元が分からない構成ではユーザー名ごとに数える。
  - 正しいパスワードでのログインは、使った枠を返す。
- メールを送らせる申し込み (サインアップ・再設定) は接続元ごとに10分5回、全体で10分50回。
- パスワードの変更と、メールアドレスの変更の申し込みで今のパスワードを照合するときは、ユーザーごとの同じ枠で数える。セッションだけを奪った相手に総当たりさせないため。

### メールのリンク (`src/email_token.rs`)

- サインアップの確認・パスワードの再設定・メールアドレスの変更は、どれも1回限りのトークンを載せたリンクで行う。DB にはトークンの SHA-256 だけを置く。
- 有効期限は確認が24時間、再設定とメールアドレスの変更が1時間 (乗っ取りに直結するため短い)。
- 使われていないリンクを送ってから5分以内の申し込み直しでは、発行し直さずメールも送らない。第三者の申し込み直しで、本人に届いたリンクを潰し続けられないようにするため。
- 申し込みの応答はアカウントの有無に関わらず同じにし、アカウントの検索から送信までを応答の後で行う (`tokio::spawn`)。応答の中身と時間から、そのアドレスが使われているかを探らせないため。

### サインアップ (`src/signup.rs`)

- 申し込みではメールアドレスだけを受け付け、パスワードを持たない未確認のアカウントを作る。パスワードは確認リンクの先で設定し、その時点で確認済みにしてログインさせる。
- 申し込みでパスワードを受け付けないのは、他人のメールアドレスで先に登録されても乗っ取りの経路にしないため。未確認のアカウントは誰もログインできないので、本人の登録し直しや外部のログインでそのまま引き継げる。
- 登録済みのアドレスへの申し込みでは、確認リンクの代わりにログインの案内を送る。
- 確認リンクの期限が切れた未確認のアカウントは、定期処理 (後述) で消す。

### パスワードの再設定と変更

- メールでの再設定 (`src/password_reset.rs`) は確認済みのアカウントにだけリンクを送る。未確認のアカウントには確認リンクを送り直す。
  - パスワードを持たない外部のログイン専用のアカウントにも、再設定でパスワードを持たせる。メールを受け取れたことが本人の確認になるため。
  - 再設定したらそのアカウントのセッションをすべて断ち、ログインはさせない。
- 本人の変更 (`PUT /api/v1/account/password`) は今のパスワードを照合し、変更した端末以外のセッションを断つ (後述の世代)。
- 管理者は管理画面から他人のパスワードを再設定できるが、自分自身にはできない (今のパスワードの照合を迂回させないため)。端末の `--reset-password <ユーザーID>` は管理者自身を含めて誰でも再設定できる。どちらも対象のセッションをすべて断つ。
- パスワードが変わったら、どの経路でも本人にメールで知らせる (`src/password_notice.rs`)。

### メールアドレスの変更 (`src/email_change.rs`)

- 変えるのはユーザーID (`users.username`)。新しいアドレスに送ったリンクの先で確定する。リンクを開いただけでは変えず、確定の操作を求める (メールの安全確認でリンクを先に開くサービスがあるため)。
- パスワードを持つアカウントは、申し込みに今のパスワードを求める。
- 確定したら、そのアカウントに出したリンク (古いアドレスに送った再設定など) をすべて使えなくし、古いアドレスに変わったことを知らせる。セッションは断たない。
- 新しいアドレスを確認済みのアカウントが使っていれば変えない。未確認のアカウントが使っていれば、確定のときに消す。凍結中のアカウントは変えない。

## セッションと CSRF

- セッションは `tower-sessions` と SQLite のストアで、期限は最後のアクセスから `[session] expiry_days` 日 (既定30日)。署名鍵は `[session] secret` が空なら自動で作り、ファイルに保存する (`src/session.rs`)。
- ログインに成功したら `session.cycle_id()` でセッション ID を変える (セッション固定攻撃の対策)。
- `secure_cookie` が有効なときは、セッションと `state` の Cookie の名前に `__Host-` を付ける (`__Host-id` など)。同じ登録ドメインの別のサブドメインが乗っ取られても、`Domain` 付きの同名 Cookie を送り込んでセッションや `state` を差し替えられないようにするため。

### 世代によるセッションの無効化

- `users.session_generation` をセッションにもコピーして持たせ、`AuthUser` の抽出のたびに DB の値と比べる。ずれていたらそのセッションを破棄して 401 にする。
- パスワードの変更・再設定で世代を上げる。本人の変更では、操作した端末のセッションだけを新しい世代に載せ替えて残す。
- ユーザーごとにセッションを選んで消す方式は採っていない。ストアの `data` は MessagePack の BLOB で、SQL から `user_id` を引けないため。
- 同じ `AuthUser` の抽出で、ユーザーが消えていたり凍結中だったりしても、セッションを破棄して 401 にする。

### CSRF

- トークンは使わず、GET 以外のリクエストで `Origin` (無ければ `Referer`) をリクエスト自身のオリジンと比べる (`src/csrf.rs`) のと、セッション Cookie の `SameSite=Strict` を組み合わせる。
  - `SameSite` は同じサイト単位の制限で、同じ登録ドメインの別のホストからの送信は防げないため、ホスト単位の比較で補う。
  - 比べる先の host は、信頼済みのプロキシが伝えた `X-Forwarded-Host` があればそれ、無ければ `Host`。scheme は、信頼済みのプロキシが proto を伝えたときだけ比べる (`src/forwarded.rs`)。
  - `Origin`・`Referer` のどちらも無いリクエストは通す (ブラウザ以外のクライアントのため)。
- 例外は Apple のコールバックと、モバイルアプリのオリジンからのリクエスト (docs/mobile-app.md)。

## 管理者

- 最初の管理者は端末で `--create-user <名前> --admin` を実行して作る。最初の行を自動で管理者にするような暗黙の規則は持たない。
- 管理 API は `auth::AdminUser` (`users.role = 'admin'` を求める抽出) で守る。
- 自分自身の凍結・削除はできない。有効な管理者 (凍結も削除予約もされていない管理者) が残らなくなる凍結・削除は、同じトランザクションで確かめて断る。
- 管理者による閲覧と操作は、誰が・いつ・誰に・何をしたかを `admin_audit_log` に残す (`src/audit.rs`)。記録の閲覧は、API で記録を返すたびに1件残す。

## アカウントの削除 (`src/account.rs`)

- 削除はすぐには行わず、30日の猶予を置いた予約として `users.deletion_scheduled_at` に記録する。予約中もログインと操作はそのまま使える。
- 予約の起点を `users.deletion_origin` に持ち、取り消し方が変わる。
  - `user` (本人): 本人がログインすると取り消す。専用の取り消しの操作は無い。
  - `admin` (管理者): 本人のログインでは取り消さず、管理者だけが取り消せる。凍結中の本人がログインを試すだけで取り消せると、管理者の削除が届かないため。
  - `inactive` (自動退会、後述): ログインに加えて、セッションでの操作でも取り消す。
- 予約済みのアカウントに重ねて予約しても、予定日と起点は最初の予約のまま変えない。
- ログインでの取り消しは凍結の判定より前に行う。凍結された人が、自分で申し込んだ削除を止められなくならないように。外部のログインでは、`oauth_identities` で本人と分かったときだけ取り消す。
- 定期処理 (`account::purge_expired_periodically`) が起動時に1回と、その後1日に1回走り、次を行う。
  - 予定日を過ぎたアカウントの物理削除。消す前に LINE・Apple との連携を取り消す。記録などは外部キーの `ON DELETE CASCADE` で一緒に消える。
  - 確認リンクの期限が切れた未確認のアカウントの削除。
  - 放置アカウントの自動退会の予告と予約。

### 放置アカウントの自動退会 (`src/inactivity.rs`)

- `[inactivity] delete_after_days` (既定0 = 無効) を過ぎても使われていないアカウントに、通常の削除予約 (起点 `inactive`) を入れる。
- 最終アクセスは `users.last_seen_at` で、ログインとセッションでの操作で更新する (`account::touch_last_seen`)。書き込みは前回から1日以上たっているときと、自動退会の予約が入っているときだけにし、読むだけのリクエストを書き込みの競合に巻き込まない。`NULL` なら作成時刻を使う。
- 退会日の30日前・7日前・前日にメールで予告する。最後に送った予告を `users.inactivity_notice_days` に持ち、重ねて送らない。定期処理が止まっていて時期を過ぎたときは、一番近い予告を1通だけ送る。
- 管理者・凍結中・削除予約済み・買い足した OCR の枠が残っているアカウントは対象にしない。
